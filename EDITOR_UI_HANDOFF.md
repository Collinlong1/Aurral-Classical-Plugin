## Source: the editor review's seven recommendations

The user supplied the original review text on November 15, 2026; it was not in either repository before. Verbatim:

1. **Protect unsaved edits across all actions.** Navigation checks for unsaved changes, but other actions bypass that check. For example, edit a work's title, then move a movement or add a credit: the successful action refreshes the page and can reset the unsaved title. Preserve drafts per form, or require Save/Discard before another action changes the entry.
2. **Turn album assignment into one focused workflow.** Currently an album can show its works, unmatched tracks, assigned tracks, an existing-work form, and a new-work form together, with tracks repeated in mapping controls. Use: Select tracks → Choose existing work or Create new → Check movement mapping → Apply. Show the selected tracks once, with a persistent "6 tracks selected" action bar. Keep the album context visible throughout.
3. **Give work editing clear sections.** A work currently stacks Details, Movements, Add movements, Credits, Add credit, Recordings, Add broadcast, and Merge. Use Details · Movements · Credits · Recordings navigation within the work. Open Add credit/Add broadcast only when requested; put Merge/Delete under an Actions menu.
4. **Make lookup fields work smoothly with the keyboard.** The work/composer picker handles Escape, but lacks arrow-key selection and Enter-to-select. Focusing it also clears the displayed search text. Support standard combobox behavior, retain the selected label, and distinguish "Searching," "No matches," and "Search failed." The main list search should either update after a short pause or visibly offer a Search button.
5. **Keep Save and feedback near the task.** Save sits at the bottom of each form, while success/error messages appear near the top of the detail pane. Long mappings can leave both inconveniently placed. Use a persistent Save/Cancel footer for the active task, show "3 unsaved changes," and put validation beside the affected field.
6. **Simplify movement reordering and review decisions.** Reordering currently saves each Up/Down click separately. Allow local reordering followed by one Save order, with keyboard controls and optionally drag handles. Reviews should lead with the question and two clearly named entries, then offer Merge, Keep separate, or Skip; choose the surviving entry inside the merge step instead of exposing several long directional buttons.
7. **Keep list navigation stable.** Internal links currently clear the search and switch the list's tab. Preserve each tab's search, page, and scroll position so returning from a movement or composer brings you back to where you were.

**Item 5 gaps against this text** (item 5 was rebuilt from the previous session's summary, which omitted them): the footer says "Unsaved changes" without a count, and validation errors appear in the form footer, not beside the affected field. Field-level placement needs a generic way for a plugin's rejection to name a field (a bounded optional `field` on `{ok:false}` results, passed through by core). Not yet done; raised with the user.

- Core (generic): v2 forms gain an `order` field type, following v1's order-field convention (value = item values in order, `options` name them). Items are rearranged locally by drag handle, keyboard drag (Space, arrows, Space; dnd-kit announcements via the shared `SortableList`) or per-item ↑/↓ buttons (`TooltipButton`). Submit saves once; the item-5 footer gives Discard and the unsaved note. The host sends `capabilities.orderField: true`. An old core rejects the page with 502 on an unknown field type (observed in the red host test), so the plugin sends order fields only with the flag. The handle is a plain button styled like `PlayerQueue`'s: the repo lint requires `TooltipButton` for `.btn` icon buttons, and the handle needs dnd-kit's activator ref.
- Plugin (1.0.58): Movements has **Reorder movements** (`work!reorder`, Cancel back to Movements). New hosts get the order field. Older hosts get one position menu per movement: change a number and the rest keep their order around it. Both submit `set-movement-order`, which checks the order the page showed (409 when the movements changed) and writes positions once. Per-click Move up/down is gone for works up to 500 movements; above that the form limit applies and step moves remain. The merge message points to Reorder movements.
- Reviews about two entries (duplicate works, an identity held by another work/person, same-name composers) lead with **The question** (question, this entry, the other entry), then **Decide**: Merge… / Link the record here instead (identity only) / Keep separate / Skip, each with what it does. The header keeps only navigation (Open entry, Open the other work). Keep separate uses `keep-distinct` for duplicates (remembered) and closes the item otherwise.
- **Merge step** (`merge:<opened>:<other>[:<review>]`, revision scope covers both entries and the review): both outcomes ("If “X” (the one you opened · N recordings) stays" / "(the other · …)"), then the form choosing **Entry that stays** ("The one you opened" / "The other one"; default the one with more recordings or credits), then the works side by side.
