# Aurral Classical review: Codex Phase 2–4 work vs. Scope v3

Reviewed November 11, 2026. Branches: plugin `phase4-review` (`a176414`, which contains phase2/phase3) and core `phase4-review` (`be77fb7`). Both build on the merged Phase 1 `aurral-classical` branches. Compared against *Aurral Classical — Updated Scope v3* (Nov 10, 2026).

**Verification done here:** read the code. The plugin suite passes (181/181, Node 22) and the committed `index.js` bundle matches `src/`. I also ran a throwaway probe against the real model code to confirm findings B1 and B2. I did not run the browser/Compose suites or the core suite again.

---

## 0. Summary

Codex built good, carefully tested **data-layer** pieces. But it built the whole product on the **architecture that Scope v3 replaces**. The model, editor, album "By Work" view, work page and bounded playback all run inside the Aurral plugin process. They render through new hooks that Codex added to the **forked core** (`pages`/admin forms, `albumPresentation`, resource pages, queue segments, `userOperations`/`localPlaylists`). Stock Aurral 3.0.0 has none of these hooks. On stock v3 even the model scan cannot start.

Inside that architecture there are also real bugs:

- **Duplicate works and duplicate composers for each album.** Confirmed.
- **Any tag change to a file silently detaches it from its work.** Confirmed.
- **The "By Work" view hides tracks** that aren't in a work.
- There is **no automatic sync** and **no review queue**.
- There are **no Send to / Remove from Aurral Classical controls**.
- The editor is a generic form engine. It doesn't fit classical metadata, which is why it's hard to use.

**Recommendation:** keep the model and provenance code, plus most tests. Stop adding to fork-core hooks. Start Transition Phase A/B from Scope v3: a stock v3 bridge plus a Classical container. Rebuild the editor as a real app inside that container (see §4).

| Minimal bridge plugin (§2) | The plugin is maximal: tagger, MB resolver, slskd source, compare, model, editor, presentation and work pages all in one process. Each page view opens SQLite inside a plugin call. | High |

**What can move to Classical largely unchanged:** `src/model/schema.js`, `catalogue.js`, `metadata.js` (provenance, pins, intentional blanks, conflicts), `database.js` (online backup, forward-only migrations), `jobs.js` (lease, checkpoint, resume), most of `reconcile.js`, `editor-search.js` (accent-insensitive search), and the MB/resolver/`works.js` code. Most of `test/model.test.js` and `test/editor.test.js` (the backend command tests) move with them.

**What stays in the bridge:** classification hints, an endpoint that lists the library, an event forwarder (`download.finished` → Classical), the slskd `downloadSource`, and possibly the Send/Remove menu actions.

**What gets replaced:** fork `PluginPage`/`PluginResourcePage`/AlbumPage presentation, `pages`/`albumPresentation` manifest entries, and `UserOperations`.

**What to retire after parity:** the queue-segment changes in the core player. Nothing creates a non-whole segment today (`segment(track, { kind: "whole" })` everywhere), so these player changes add risk to stock playback without being used.

## 2. Bugs (independent of architecture)

### B1. Each album creates its own work and its own composer (confirmed)
`src/model/auto-match.js:86` keys each group by `albumId`. `composerEntity()` (`:132`) **always** creates a new person.

Probe result: two albums of Beethoven 5 with identical WORK/composer tags give **2 works, 2 "Ludwig van Beethoven" people and 4 recordings**. The MusicBrainz parent-work path also keeps `albumId` in the key, so even a shared MB work ID doesn't merge them. As a result:

- the work page can never show "all owned recordings" (§5 Foundation);
- comparing performances fails;
- the composer list fills with duplicates;
- this breaks "Avoid duplicate works and recordings" (§4).

**Fix:**
1. Resolve works by `external_identity` (MB work ID, or a normalized composer + catalogue + title key).
2. Resolve composers by MB artist ID or alias table, and send ambiguous cases to review.
3. Create a work once, then add one performance/realization per album.

### B2. Any tag edit detaches the file from its work (confirmed)
The fingerprint is a **whole-file** SHA-256 (`runtime.js:14`, `:192`). `reconcile.js:15` rejects a match whenever fingerprints differ.

Probe result: after a retag, the original link (with its segment) goes to `review` and a new, unattached `active` link is created. The track disappears from By Work and the work page.

This is triggered by:
- this plugin's own tagger (`tag-album`, `tag-artist`, background tagging);
- Aurral 3 genre tagging on download;
- Picard or any other tagger.

It breaks "survive rescans" (§7) and "fallback fingerprint for rescans" (§4).

**Fix:** fingerprint the audio stream only (decoded-frame hash, or a hash that skips tag blocks). Treat a matching core ID + file ID + path + duration as the same file even if the tags changed.

### B3. Nothing syncs automatically
`scheduled()` only continues a scan that is already queued (`runModelJobs`). It never starts one, and `enqueueModelScan` requires an admin user and the fork grant. `download.finished` feeds only the tagger, and only when `enableFileWrites` is on.

New downloads, deletions and changed files therefore never reach Classical until an admin clicks "Scan" in an album menu. This breaks §4: events plus periodic incremental reconciliation.

### B4. Every scan re-hashes and re-writes the whole library
- Every scan hashes **every byte of every file**. There is no size/mtime/inode shortcut, which is why the first real scan reached only 60 of 12,802 files.
- `model_job.input` holds the whole file list. At each 10-file checkpoint, `progress.collected` (every hint for every file so far) is serialized again, so write volume grows quadratically.
- Each completed scan inserts one `track_evidence` row and one `audit_event` per track, so the database grows without bound.

**Fix:** do incremental scans keyed on (file ID, size, mtime). Hash only new or changed files. Store collected rows in a staging table instead of JSON. Prune evidence and audit history.

### B5. One bad file fails the whole scan
`runtime.js:205` throws *"Missing track duration"*. A `realpath` on a file Aurral still lists but that is gone from disk throws `ENOENT`. A file that changes mid-read also throws. Any of these makes the whole job fail (`jobs.fail`, `:314`) after 3 attempts.

**Fix:** record a per-file error, skip the file and keep going.

### B6. Classification is new code, not the existing logic, and most of it can never fire
- Scope §4 says to use the **existing** classification logic, meaning Phase 1's resolver and MB work relations. The model instead uses a new score in `reconcile.js:221`.
- The scan never sets `hints.movement`, `hints.classicalComposerRelation` or `hints.catalogueNumber`, so those terms can never score. In practice, "classical" means a WORK tag or a classical-genre tag.
- A track with no genre tag scores 0 and ends up `unsure`. That includes most pop as well as untagged classical. Each `unsure` track opens a review item, and **no review queue UI exists** to clear them.

**Fix:** call the Phase 1 resolver (MB recording → work → composer relation) as the main signal, and fill in the missing hints.

### B7. "By Work" hides tracks that aren't in a work
In `AlbumPage.tsx:847` the native TrackList renders only in "By Track" mode, and "By Work" is the default (`:125`). On a mixed album, encores, fillers and non-classical tracks vanish from the default view.

The work list items are also plain `<li>` text. You can't play a single movement, there are no durations or menus, and the only action is "Play whole work".

### B8. Saving fails while a scan is running
The editor revision is `max(audit_event.id):max(assertion.rowid)` across the whole database (`editor.js:39`). Every scan commit, auto-match, another admin's edit, or an edit to a *different* entity changes it. An open form then gets HTTP 409 *"This catalogue changed"*.

**Fix:** use a per-entity `revision` column. The `track_link` table already has one.

### B9. Work page problems
In `presentation.js`, `PluginResourcePage.tsx`:

- Recording headings fall back to `Recording 3f2a9c1d` (a UUID prefix, `:191`). Editor-made realizations have no label, and auto-match labels them with the album title only. No performer, conductor or year is shown, because auto-match never adds performer credits.
- You can't clear "Your pick" or the admin pick from the UI.
- A pick that is really the admin fallback is labelled "Your pick (admin fallback)".
- The mutation has no `onError`, so failures are silent.
- A non-admin sending `admin-pick` gets *"Unknown work action"*.
- "Library" links to `/library/albums`, not to the album you came from. There's no composer link and no "Edit" link for admins.
- The work page can only be reached from an album's By Work view. There is no way to browse or search works or composers (§5 Foundation/Search).

### B10. Album pages scan the entire catalogue on every load
`renderAlbumPresentation` loads **every** realization item in the catalogue and filters by album in JS (`presentation.js:93`). This runs on every album page view, for every user and every album, including non-classical ones. Stock album pages now pay for an extra plugin process call, which conflicts with "non-classical behavior unchanged".

### B11. Compare and the model disagree on what a work is
`compare-track`/`compare-album` group by MB work ID taken from tags (Phase 1 resolver). They ignore the catalogue. Works created in the editor, fixes and pins don't affect comparisons, and Compare still needs the fork's `localPlaylists`.

### B12. File writes are not actually "off by default"
`enableFileWrites=false` only controls *background* tagging. "Tag as classical" (album/artist), "Clear classical fields" and "Restore original" write files immediately, with no preview or conflict check. That breaks §4 ("off by default; later admin-only with preview, conflict detection, backup/undo"). Combined with B2, these actions also break Classical's own links.

### B13. Scope features missing or misnamed
- **Send to Aurral Classical / Remove from Aurral Classical** don't exist. The only manual inclusion is the "Confirm classical" checkbox when attaching a track in the editor, and there is no exclusion at all. "Tag as classical" (which writes files) is still the menu item (§4).
- Whole-library actions ("Scan…", "Cancel…", "Classical model status") sit in **album** menus but act on the entire library. That confuses users, and Codex's own guide has to explain it.
- `auto-match.js:5` `MULTI_MOVEMENT` leaves out mass, requiem, cantata, oratorio, opera, variations, sinfonia and string quartet "No." patterns when there's no WORK tag. Auto-made movement titles copy the full track title, e.g. "Symphony No. 5 in C minor, Op. 67: I. Allegro con brio".
- Auto-match creates **one recording entity per movement track** (`auto-match.js:185`), not one per performance. The editor's item list then fills with "Recording · Untitled recording" entries.

### B14. Documentation that is wrong or misleading
- `PHASE_4_REPORT.md` says broader provider-parent matching is "later work". But `autoMatchWorks` already does MB parent-work lookups (`runtime.js:335-375`), and the action's message advertises it.
- The reports describe "stock hosts" as keeping model actions, but on stock hosts the scan can't run (see §1).
- The reports claim "no duplicate" safety, but cross-album duplicates are built in (B1).
- `AGENTS.md`/`HANDOFF.md` still describe the fork plan and should be updated to Scope v3.

## 3. Why the metadata editor is hard to use

The editor is a **generic, server-defined list of forms** (`PluginPage.tsx`) driven by `src/model/editor.js`. It was built to fit inside the fork without plugin scripts. These are the reasons it feels unusable:

**Navigation**
1. **One flat list** of every composer, work, **movement**, performance, recording and person. It's sorted by creation time, 100 per page, with Previous/Next only. There's no filter by type and no hierarchy (composer → works → movements → recordings).
2. Movements appear as top-level rows ("Movement · I. Allegro") with no parent work. Auto-match adds thousands of "Untitled recording" rows (B13).
3. Links between items aren't clickable. A work's recordings are a single semicolon-joined note (`editor.js:409`). A movement has no link back to its work, and a recording has no link to its tracks.

**One search box for unrelated jobs**
4. The page-level "Search items" box **filters the item list, the track picker, the composer dropdown and the contributor dropdown all at once** (`editor.js:104`, `:132`, `:219`, `:425`). Searching for a track to attach can make the "Add credit" form **disappear** if no contributor matches. Searching a performer name narrows the composer list.
5. You can't search while a form has unsaved changes: search and navigation are disabled while `editingForm` is set.

**Editing**
6. **Each field is its own form** with its own Save button. A work shows about 15 stacked forms: "Edit title", "Edit nickname", "Edit description", "Edit period", "Edit form", "Edit catalogue", "Edit instrumentation", one "Provider value for X" form per pinned field, Add movement, Movement order, Create broadcast, Add credit, Credits. **Only one form can be dirty at a time**, so you can't fix a title and a nickname in one save.
7. Labels are raw internal keys ("Edit movementNumber", "Edit catalogue"). Roles are lowercase raw values ("soloist"). Help text shows `Source: provider · Pinned override` and `Provider value: "Symphony No. 5"` as raw JSON with quotes.
8. Pin semantics are confusing. "Pin this value" is **pre-checked whenever any provider value exists** (`editor.js:326`), so saving an unchanged field pins it. "Intentionally blank (null)" is a checkbox next to the text box and silently overrides whatever you typed.
9. Fields that matter for classical are missing: **key** (C minor), **aliases/nicknames for search**, composer birth/death, and catalogue numbers as structured "BWV 1007" rather than free lines. The schema already has `key` and `aliases`, but the editor never shows them.
10. Credits are removed through a dropdown plus a "Remove credit" button, not a list with a remove button on each row. The contributor dropdown defaults to the first person alphabetically and is capped at 200.
11. Movements can't be deleted. A movement can only be renamed by finding it in the flat list. Works, composers and recordings can't be deleted or **merged**, so B1's duplicates can't even be cleaned up by hand.

**Attaching audio (the main task)**
12. Attaching is one track at a time: select a recording, type in the global search, pick a track from a dropdown labelled `title · folder / file · unsure`, pick the movement, tick "Confirm classical", save. Then repeat for every movement, waiting for a full page re-render each time. There's no "attach this album's tracks 1–4 to movements I–IV".
13. The track-first path ("attach-found-track") offers only the **first 200 recording/performance pairs by ID** (`editor.js:531`). Its movement dropdown lists the movements of *every* work (up to 999, `:562`), not the chosen recording's work. Picking the wrong one is easy, and the server rejects it.
14. There's no review queue. Unsure classifications, provider conflicts and track links in "review" (B2) can't be seen or resolved.

**Performance**
15. Every page view loads all entities with a correlated subquery, all owned tracks (12,802 evidence JSON parses), and runs a composer query per person. Rendering is roughly O(N²) (`entityType` → `composers.some`). This is noticeably slow on a real library.

## 4. What the editor should look like (in the Classical container)

Build it as a normal SPA page in the Classical frontend, not as server-defined forms.

**Layout:** three panes on desktop, stacked with a back button on phones.
- **Left:** browse by **Composers / Works / Recordings / Albums / Review (n)**, with type filters and search *scoped to that list*.
- **Middle:** a tree for the current item, e.g. composer → works → movements, or album → tracks.
- **Right:** the detail editor.

**Work detail is one form with one Save:**
- Title, nickname, key, catalogue (structured: system + number, e.g. BWV 1007), period, form, instrumentation, aliases, description.
- Each field shows a small provenance chip (**MB** / **Manual · pinned** / **Blank · pinned**) with a ⋯ menu: *Use provider value*, *Pin*, *Mark intentionally blank*, *Show history*.
- When the provider value differs from the shown value, show it inline in grey ("MusicBrainz: Symphony No. 5"), not as raw JSON.
- Pin automatically when a provider value is changed. Never pin a field that wasn't changed.
- Movements are an editable table: drag to reorder, rename inline, add, delete. Show which recordings cover each movement.
- Credits are a table with role dropdowns, an instrument field and a remove button on each row. "Add credit" searches people and ensembles with its own search box.

**Attach audio album-first** (the common case):
- Open an album and choose **Assign to work…**. Pick or create the work (with a duplicate check, "Beethoven: Symphony No. 5 already exists"), then see a two-column matcher: album tracks on the left, movements on the right.
- Pre-fill the matches from track order and title similarity. The admin adjusts and confirms once. Excluded tracks are skipped.
- **Send to / Remove from Classical** and the classical/not/unsure override are buttons on the same screen.

**Review queue:**
- Tabs for *Unsure classification*, *Provider conflicts*, *Lost track links* (with candidate files), *Possible duplicates* (with **Merge**).
- Each item has one-click Accept / Reject / Open.

**Other:**
- Edit only the entity you're saving (per-entity revision, B8).
- Warn about unsaved changes on navigation instead of disabling the whole page.
- Every name links to its page.
- On the public work page, admins get an **Edit** button that goes straight to that work.

## 6. Things Codex got right (keep these)
- Provenance model: per-field assertions, manual vs. provider, pinned values that survive refresh, intentional blanks, kept conflicts, audit trail.
- Safety: SQLite online backup before migrations, forward-only transactional migrations, read-only media checks, leased and resumable jobs, generation/epoch fencing on reconcile.
- Validation: the server checks every editor command (allowed fields, entity kinds, movement belongs to work, duplicate credits), and failed commands roll back cleanly.
- Accent- and punctuation-insensitive search (`editor-search.js`).
- Per-user favourites and picks with an admin fallback (`user_work_state`, `admin_work_pick`). Keep the schema and move it to Classical.
- Synthetic fixtures, recorded provider data, no production access. The 181 plugin tests are a good base to carry over.
